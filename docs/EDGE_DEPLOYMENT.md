# 엣지 배포 명세 (라즈베리파이5 + DeepX DX-M1)

협업사(클리카) 요청 3건에 대한 답변. **실측값과 추정값을 구분해 표기**한다.

---

## 1. 세포 검출 모델 파일

### 제공 형식

학습 포맷 `.pt` 그대로 제공. GitHub Releases 태그 `weights-v1`.

명명 규칙: `<모델>_f<fold>.pt` — 예 `yolov8x-seg_f0.pt`

변환 대상으로 **권장하는 우선순위**:

| 순위 | 모델 | 근거 |
|---|---|---|
| 1 | `yolov8n-seg_f0.pt` (6.8 MB) | 계수정확도 0.9691, CPU 86 ms. 크기·속도 대비 성능 최적 |
| 2 | `yolo11n-seg_f0.pt` (6.0 MB) | 가장 작고 빠름(CPU 75 ms). 단 5-fold 검증은 진행 중 |
| 3 | `yolov8x-seg_f0.pt` (144 MB) | 정확도 최고 0.9756. NPU 메모리 여유 있을 때만 |

> 정확도 차이가 0.65 %p 뿐이므로 **엣지에는 nano 계열을 권장**한다.
> 모델 크기는 21배 차이난다.

### 모델 명세

| 항목 | 값 |
|---|---|
| 프레임워크 | Ultralytics YOLO **8.4.150** / PyTorch **2.11.0+cu128** |
| 태스크 | instance segmentation (`task=segment`) |
| **입력 해상도** | **512 × 512** (타일 단위) |
| 입력 포맷 | RGB 3채널 uint8, NCHW, 배치 1 또는 9 |
| 입력 정규화 | `/255.0` 만 적용. 별도 mean/std 없음 |
| **클래스 수** | **1** |
| **클래스 목록** | `0: cell` |
| 출력 | 박스(xywh+conf) + 마스크 프로토타입. `retina_masks=True` 시 원본 해상도 마스크 |
| 권장 conf | 0.55 (yolov8n) / 0.65 (yolov8x). 모델별로 다름 |
| NMS IoU | 0.5 |
| max_det | 300 (실제 장당 세포 6~22개이므로 여유 충분) |

### ⚠ 원본 영상은 512가 아니라 1376×1032 — 타일링 필수

| 단계 | 값 |
|---|---|
| 원본 영상 | 1376 × 1032 |
| 타일 크기 | 512 × 512 |
| stride | 432 (오버랩 80 px) |
| 타일 수 | **3 × 3 = 9 타일 / 영상** |
| 업스케일 | 없음 (1:1) |

세포 등가직경이 53.8 px 이므로 원본을 단일 512 입력으로 리사이즈하면
세포가 ~20 px 로 줄어 마스크 품질이 떨어진다. **반드시 타일 단위로 추론**해야 한다.

타일 좌표 생성과 병합 로직은 `code/evaluate.py` 의
`tile_origins()` / `merge_instances()` 참조.

### 후처리 (NPU 외부, CPU 담당)

1. 타일별 인스턴스 마스크를 원본 좌표계로 배치
2. 오버랩 영역 중복 제거: 마스크 IoU ≥ 0.3 **또는** 포함비 ≥ 0.6 → 점수 높은 쪽 유지
3. 면적 < 150 px 제거
4. 최종 인스턴스 개수 = 세포 수

**watershed 는 사용하지 않는다.** 이 데이터는 접촉 세포가 0건이라
(GT 에서 Tw 0.4~0.9 전 구간 추가분리 0건) watershed 가 과분할만 유발해
계수정확도를 떨어뜨렸다. 참고 논문의 Tw=0.65 는 WBC 데이터 고유 결과다.

## 2. 타깃 환경 정보

### 하드웨어 — 확인 및 보완

클리카가 이해한 **라즈베리파이5 + DX-M1 표준 구성이 맞다.** 다만 당측 배포 대상은
복수이므로 아래를 함께 고려해 주시기 바란다.

| 대상 | 용도 | 우선순위 |
|---|---|---|
| 라즈베리파이5 + DeepX DX-M1 | 인라인 모니터링 주 타깃 | **1 (금번 요청 범위)** |
| NVIDIA Jetson AGX Orin / Thor | 고처리량 랩 장비 | 2 (별도 진행) |
| 범용 x86 CPU | 백업·검증 경로 | 3 (별도 진행) |

### 목표 FPS

**목표: 2 fps (영상 1장/0.5초) — 타일 9개 기준 18 tile/s**

근거:
- 용도가 바이오프로세스 **인라인 모니터링**이며, 세포 농도는 분 단위로 변하므로
  초당 수십 프레임이 필요하지 않다.
- 장당 세포 6~22개를 1초 내 계수하면 현장 요구를 충족한다.
- 여유분 포함해 **최소 1 fps, 목표 2 fps, 희망 5 fps** 로 설정한다.

### 참고 실측 — 개발 머신 (엣지 실기 아님)

입력 1장 = 타일 9개 일괄 추론. warmup 5회 후 20회 측정, 중간값.

| 모델 | ckpt | RTX 5090 FP32 | RTX 5090 FP16 | x86 CPU FP32 |
|---|---:|---|---|---|
| yolo11n-seg | 6.0 MB | 7.5 ms (133.9 fps) | 6.6 ms (150.8 fps) | 75.3 ms (**13.3 fps**) |
| yolov8n-seg | 6.8 MB | 8.0 ms (124.4 fps) | 7.2 ms (139.2 fps) | 86.2 ms (**11.6 fps**) |
| yolov8s-seg | 23.9 MB | 9.6 ms (104.3 fps) | 7.8 ms (128.7 fps) | 210.8 ms (4.7 fps) |
| yolov8m-seg | 54.8 MB | 17.1 ms (58.7 fps) | 11.3 ms (88.3 fps) | 436.0 ms (2.3 fps) |
| yolov8x-seg | 144.0 MB | 39.4 ms (25.4 fps) | 21.3 ms (47.0 fps) | 1168.6 ms (0.9 fps) |

> ⚠ **이 수치는 라즈베리파이5 + DX-M1 성능을 예측하지 않는다.** 개발 머신 기준이며,
> 엣지 실기 지연시간은 변환 후 실측해야만 알 수 있다. 당측은 DX-M1 실기 미보유 상태로,
> 변환·측정은 클리카측에서 진행하는 것으로 이해하고 있다.
> x86 CPU 열은 라즈베리파이5 CPU 단독 성능의 **상한**으로만 참고해 주시기 바란다
> (Cortex-A76 2.4 GHz 4코어는 측정에 쓴 x86 대비 상당히 느릴 것으로 예상).

### CPU / NPU 작업 분배 계획

```
[카메라 1376x1032]
        │
   ┌────┴─────────────────────────── CPU (라즈베리파이5)
   │  1. 타일 분할  3x3 = 9 tiles @ 512x512   (numpy 슬라이싱, ~1 ms)
   │  2. uint8 → NPU 입력 텐서 패킹
   └────┬─────────────────────────────────────
        │
   ┌────┴─────────────────────────── NPU (DX-M1)
   │  3. YOLO-seg 추론  9 tiles 배치 또는 순차
   │     (박스 + 마스크 프로토타입 출력)
   └────┬─────────────────────────────────────
        │
   ┌────┴─────────────────────────── CPU
   │  4. NMS (타일 내)                  conf 0.55, IoU 0.5
   │  5. 마스크 디코드 → 원본 좌표계 배치
   │  6. 타일 간 중복 제거  IoU≥0.3 or 포함비≥0.6
   │  7. 면적 필터 <150px 제거 → 세포 수 확정
   └────┬─────────────────────────────────────
        │
   [세포 수 + 마스크 오버레이]
```

| 단계 | 담당 | 비고 |
|---|---|---|
| 타일 분할 | CPU | 메모리 복사만, 경량 |
| 모델 forward | **NPU** | 전체 연산의 대부분 |
| NMS | CPU 또는 NPU | DX-M1 지원 여부에 따라 결정 — **클리카 판단 요청** |
| 마스크 디코드 | CPU 권장 | 프로토타입×계수 행렬곱. NPU 가능하면 NPU |
| 타일 간 병합 | **CPU 필수** | 영상 전역 로직, 가속 불가 |

**분배 설계 시 요청사항 2건**

1. 장당 세포가 6~22개뿐이라 **NMS·마스크 디코드 비용이 작다.** 모델 forward 를
   NPU 에 몰아주는 것이 가장 효과적이다.
2. 타일 9개를 **배치로 한 번에** 넣을 수 있는지 알려주시기 바란다. 배치가 되면
   호출 오버헤드가 1/9 로 줄어 FPS 확보가 쉬워진다. 배치 미지원이면 순차 9회 호출
   기준으로 목표 FPS 를 재산정해야 한다.

## 3. INT8 양자화 Calibration 데이터셋

### 실제 생성 결과

| 항목 | 수량 |
|---|---|
| 원본 영상 | **60 장** (1376 × 1032) |
| **생성 타일** | **540 장** (512×512, stride 432) |
| 세포 포함 타일 | 520 장 |
| 빈 타일 | 20 장 (전체의 3.7 %) |
| 타일 내 세포 인스턴스 합 | 1,458 개 (※ 오버랩 중복 포함) |
| 고유 세포 수 | 743 개 |
| 밝기 범위 | 73.1 ~ 111.5 (평균 90.9) |

> 타일 세포 합 1,458 이 고유 세포 743 보다 많은 것은 **stride 432 오버랩 때문에
> 경계 세포가 인접 타일에 중복 등장**하기 때문이다. Calibration 목적에는 문제가
> 없으나(activation 분포만 필요), 정확도 평가에 이 숫자를 쓰면 안 된다.

요청하신 "실측 수백 장"은 **타일 단위 540장으로 충족**한다. Calibration 이 512×512
입력 단위로 수행되므로 타일 수가 실질 분량이며, 일반적인 INT8 권장치(100~500 샘플)를
넘는다. 단 **원본 영상 단위로는 60장**이라는 점은 명시해 둔다.

### 제공 형식

```
calib_tiles_512.zip   (100 MB)
├── cho01_0_0.png     # <영상>_<x오프셋>_<y오프셋>.png
├── cho01_432_0.png
├── ...               # 512x512, 8-bit RGB (R=G=B), PNG 무손실
└── manifest.json     # 타일별 원본파일·오프셋·세포수·평균밝기
```

`manifest.json` 상단에 집계 메타(타일 수, 밝기 분포, 타일 규격)가 들어 있다.
생성 스크립트는 `code/make_calib_set.py`.

### Calibration 시 주의사항 2건

1. **밝기 분포를 고르게 샘플링할 것.** 영상 평균 밝기가 74.8 ~ 109.2 로 분포한다
   (평균 90.8). 특정 밝기대에 편중된 calibration 은 INT8 스케일을 왜곡한다.
2. **빈 타일을 과도하게 넣지 말 것.** 전경 비율이 2.14 % 뿐이라 빈 타일이 많으면
   activation 분포가 배경 쪽으로 쏠린다. 세포 포함 타일 중심으로 구성하고,
   빈 타일은 10~20 % 수준으로 제한하는 것을 권장한다.

### 추가 데이터 필요 시

현 60장은 **단일 배치**다. 독립 배치 데이터가 확보되면 calibration 과
일반화 검증 모두 개선된다. 당측에서 추가 촬영이 필요한지 알려주시기 바란다.

## 함께 전달하는 미검증 항목

배포 설계에 영향을 줄 수 있으므로 명시한다.

| 항목 | 상태 |
|---|---|
| DX-M1 실기 지연시간·정확도 | **미측정** (실기 미보유) |
| INT8 / FP16 양자화 후 정확도 열화 | **미측정** |
| 독립 배치 일반화 | **측정 불가** (단일 배치 60장) |
| DX-M1 의 segmentation 마스크 출력 지원 여부 | **확인 요청** |
| 타일 배치 추론 지원 여부 | **확인 요청** |

정확도 수치의 통계적 한계: fold 당 홀드아웃이 12장(약 150 세포)이라
세포 2~3개 오차가 1.5 %p 를 움직인다. 0.9756 과 0.9691 의 차이는
이 분해능 내에 있으므로 모델 선택 근거로는 **크기·속도를 우선**하는 것이 합리적이다.
